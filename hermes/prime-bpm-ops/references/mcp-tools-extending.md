# Extending the prime-bpm MCP toolset

Touchpoints (all paths under `backend/`):

1. **Tools** — `app/mcp/tools/<topic>.py`: thin wrappers over a manager method. Copy the `weekly.py` pattern: `_json`, `_err_message`, an `_with_*_session` helper (scope check → active-user check → factory/session → rollback on error), one `@mcp.tool` per operation, `PermissionError` re-raised, `BadRequestError`/`NotFoundError` → `RuntimeError(detail)`, everything else → generic RuntimeError + `logger.exception`.
2. **Registration** — `app/mcp/server.py` calls `register_*_tools(mcp)` at import time. A tool absent here is invisible to `tools/list`.
3. **Scope gate** — `app/mcp/auth.py`: `require_scope(name)` / per-topic helpers; each tool calls its gate.
4. **PAT scopes** — `app/managers/api_tokens.py::_validate_scopes` is now a generic subset-of-ALLOWED check (new scope = add it to the ALLOWED set, no validator edit). A new scope threads end-to-end: `ALLOWED_SCOPES` in `api_tokens.py` → a named constant in `app/mcp/auth.py` → per-tool gate → frontend `frontend/src/api/tokens.ts` (option list AND its separate DEFAULTS list) → `ProfilePage.test.tsx` — all in one change. Two traps:
   - Keep the UI's DEFAULT scope list decoupled from the checkbox option list: a new scope added to the options must default OFF (opt-in). Coupling defaults to options silently grants every future scope to existing minting flows.
   - The UI's token-creation form sends only `name` — a UI-minted PAT gets the default scope list WITHOUT the new scope. Mint scoped tokens via REST `POST /api/v1/tokens` with `scopes` in the body (the REST handler accepts it even though the UI doesn't). Existing PAT rows also keep their old scope lists — after shipping a new scope, mint a token with it and swap it into `~/.cursor/mcp.json` AND the Hermes MCP config, or every new tool returns `scope denied`.
   - Tests mint tokens via `tests/security/_mcp_helpers.py::auth_actor` and `tests/security/conftest.py` mock — widen the default scopes there too or the new-tool tests fail on scope, not on logic.
5. **Access model** — write tools mirror the REST handler, not invent checks. Example: roadmap add-task (`app/api/handlers/v1/roadmap.py::add_roadmap_task_v1`) does only `resolve_project_id` → `require_plan_access` → manager call → `log_history` → `notify_with_mirrors`; no tab/section-access check. Some managers (`roadmap.add_task`) commit inside the manager — the MCP session helper must then do rollback-only, never a second commit.
6. **Tests** — `tests/security/test_mcp_{scopes,parity,section_access,idor,no_discovery,auth,roadmap,projects,feedback}.py` + `tests/logic/test_api_tokens_scopes.py` (scope validation is unit-level, no Postgres). Parity tests assert MCP calls the same manager methods as the REST handler; every new write tool needs one. The parity suite also pins the advertised tool list, and `tests/docs/test_mcp_md_contract.py` pins `docs/mcp.md` INCLUDING the tool COUNT — update doc + contract test in the same commit as the catalog change. Security tests use TestClient and re-enter lifespan (that's why `server.py` rebuilds the HTTP app per lifespan enter — don't "simplify" that away).

Coverage gate: `pytest tests/security -k mcp tests/logic/test_api_tokens_scopes.py --cov=app.mcp` must hold 100% on `app/mcp` — cover the deny branches (no scope, no project access, NotFound, BadRequest, inactive user) and the generic `except Exception` sanitizer (assert the client-visible text does NOT contain the internal detail, but DO expect the SDK's `Error executing tool <name>` prefix). Error-branch tests parameterize over (tool, args, manager method, exception) — one test per branch class. To hit 100% on a new tool file, cover every input-validation branch too (per-field limits) plus the generic `except Exception` sanitizer for every tool wrapper.

Every deny test needs a POSITIVE CONTROL in the same fixture family: a deny fixture whose token carries other scopes can let a same-domain call pass the gate and then fail later on an unmocked manager — that later failure looks like deny coverage but proves nothing about the gate. Make deny fixtures scope-honest (a feedback-deny fixture holds ONLY `feedback:write`, a weekly one ONLY `weekly_plan:personal`) and prove the deny as `isError` + "manager method not called"; pair each deny with a same-scope success test so the gate's positive path is exercised in the same run. Also: only assert mocks for methods the fixture's manager actually mocks — asserting "not called" on a real (unmocked) method is meaningless.

Read tool results in MCP tests via the shared helpers (`parse_json_body` / `json.loads(tool_result_text(...))` from `_mcp_helpers.py`) — hand-parsing the SSE/text envelope produces flaky assertions that fail on response shape, not logic.

Test-infra rule: `Manager` is a SINGLETON, so `mcp_mgr.roadmap.x = AsyncMock(...)` leaks into every later test in the process and mass-fails unrelated files. Always override via `monkeypatch.setattr(...)` or a fixture that snapshots/restores — never bare attribute assignment. When the full suite fails, prove it's not your diff by stashing changes AND moving your new untracked test files aside (stash skips untracked files, so a fixture-only-in-new-file disappears and the baseline run lies), re-run, compare, restore.

Integration tests that need Postgres run against `docker compose up -d db`; the local volume may carry an OLD schema (e.g. missing newer columns) — schema-mismatch errors there are environment, not your diff; stop the container afterwards (`docker compose stop db`). Legacy suite errors from missing modules (`app.main`, `app.managers.otk/...`) are pre-existing, ignore them.

Deploy order: MR → squash-merge → pipeline → play the manual `deploy-prod` job (CI runs the restart — no server-side git pull/systemctl; see SKILL.md) → initialize + `tools/list` shows the new tool → smoke a real call → only then swap the PAT if scopes changed (mint with the new scope explicitly — defaults don't include it).
