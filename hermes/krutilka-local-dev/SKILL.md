### Password-reset recipe (verified)

Run inside the API container — it has all deps and DB access; no psql needed:

```bash
docker exec lowbid_api python -c "
import asyncio
from sqlalchemy.ext.asyncio import async_sessionmaker, AsyncSession
from sqlalchemy import select
from app.utils.default.database import get_async_engine
from app.database.models import User
from app.services.auth.passwords import hash_password
from settings import settings

async def main():
    engine = get_async_engine(params=settings.db, application_name='password-reset')
    factory = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
    async with factory() as session:
        row = await session.scalar(select(User).where(User.email=='bootstrap@test.local'))
        row.password_hash = hash_password('<NEW_DEV_PASSWORD>')
        row.session_version = (row.session_version or 0) + 1  # invalidates old sessions
        await session.commit()
    await engine.dispose()

asyncio.run(main())
"
```

Note the import paths — they differ from what the file layout suggests: engine factory is `app.utils.default.database.get_async_engine(params=settings.db, application_name=...)` (needs both args), session factory is plain `async_sessionmaker`, not a helper in `app.database`. `app.database.session` does not exist. Check `backend/app/api/lifespan.py` for the canonical wiring before scripting against the DB.

## Frontend conventions (verified in repo)

- **Two content modules, split by purpose**: visible chrome labels (tabs, buttons) live in `src/content/uiStrings.ts` (English), per-field help tooltips live in `src/content/campaignFieldHelp.ts` (Russian). When adding a control you usually need both; never hardcode the label string in the component. The user flags mixed-language chrome (e.g. a Russian tab next to English `Runtime`/`Settings`) as a bug.
- **Tests import the shared strings, not literals**: a Playwright spec that clicks `getByRole('tab', { name: 'Калькулятор' })` breaks on the next label change; import from `uiStrings`/`campaignFieldHelp` like the components do. After changing any label or dialog, grep the test tree for the old string.
- **This is a test instrument: do NOT hard-cap tunable parameters for 'realism'.** The user removed 1–3 caps on profiles-per-IP / sessions-per-day with «убери все ограничения» — realism guidance belongs in the help tooltip («обычно 1–2, но можно любое»), never in validation. Keep only sanitary lower bounds (≥1, gap ≥0) that protect the math. When adding or relaxing any bound, touch ALL layers in one change: backend `MAX_*` constants (identity/user_profile.py), API `Field(ge=…, le=…)` (api/entities/campaign_settings.py), `frontend/src/constants/campaignSettings.ts`, the help text in campaignFieldHelp.ts, and grep the test tree for the old cap — a test pinning the rejected value will fail after widening. Single-source every tunable default: API/schema output `Field(default=…)` imports the backend constant instead of re-typing the number — a duplicated literal drifts silently when only the constant changes.
- **Master enable/disable toggle goes FIRST in a settings block**, before all numeric parameters of that feature. The user flagged a feature flag sitting last in its own block as wrong (fields had been added in implementation order, flag appended last) — placement must follow the reader's logic: on/off first, then the knobs.
- **Tri-state or multi-option controls need each option explained in plain language on the question-mark tooltip** (e.g. «Включено» = what happens, «Выключено» = what happens, «Как на сервере» = inherit global), not just the field name restated. The user asks for plain-language explanations of such toggles.
- **Controlled `<input type="number">` with clamping must keep a draft string while the user types** (see `CampaignProfileSettings.tsx` NumberField): clamping `Number(e.target.value)` on every change snaps empty/garbage input to `min` (NaN → min), so the field 'sticks' at 1 and the user cannot clear or retype. Store the raw string in local state, render it, commit the clamped number on blur/Enter only. The user reported exactly this stuck-at-1 behavior as a bug.
- **After any scripted splice/regex edit of a .tsx file, run `npm run check` before claiming done** — index-based replacement of a function body can silently eat the adjacent props-interface declaration; TypeScript errors surface only in the check, not in patch diffs.
- **Actions that apply/overwrite settings open the repo's existing `ConfirmDialog` first** (title + what-will-change description + Apply/Cancel) — the user asked for this pattern on "apply recommendations"-style buttons; treat it as the default for destructive or bulk-apply actions.

## Gotchas

- **Backend dep change → rebuild image**: `docker compose up -d --build api`. A plain `up -d` keeps the stale image (happened with `itsdangerous` after auth feature). Same for workers if they share requirements.
- **Port 8000 conflicts**: stray `python -m http.server` processes from other sessions occupy it. Check `lsof -i :8000` before blaming docker.
- **Postgres queries**: `docker compose exec postgres_db` may report "not running" even when the container is up — use `docker exec lowbid_postgres_db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "..."'`.
- Full test suite (backend): run `cd backend && uv run python -m pytest tests -q`. 1000+ tests as of the adversarial-fixes wave; coverage ~75% (new modules 88-99%). `pytest-cov` is NOT in deps — `uv pip install pytest-cov` for a coverage run. e2e Playwright needs docker services up (webServer 120s timeout otherwise fails — infra, not code).
- **Treat e2e failures in layout specs (mpg-layout, mobile-nav, campaigns-reorder) as flakes until proven otherwise**: run in full parallel they sub-pixel-fail against the one shared dev server under load, but pass when the same specs are re-run in small groups (4-9 tests). Triage rule: re-run only the failing specs with lower parallelism; only if a spec fails in isolation too, suspect real code — and confirm pre-existence by stashing local changes (`git stash -u`, re-run, `git stash pop`) instead of checking out another ref's files.
- **`git checkout <ref> -- frontend/` leaves the copied files STAGED in the index.** After a ref-swap probe, restore with `git reset HEAD` + `git checkout -- <paths>` and verify `git status --short` shows no modified entries before committing anything. Probe-copied paths can also stay UNTRACKED, which then blocks switching branches: `git checkout main` refuses to overwrite untracked files that exist on main (and a `gh pr merge` will not touch them either) — just `rm` the probe-copied paths, they return from the target branch on checkout.
- **Chaos/integration tests run against LIVE Redis db15** (docker `lowbid_redis`), by repo convention (see `test_profile_store.py` for the db15 + pool-id isolation pattern) — FakeRedis only where the repo already uses it. The whole suite passes against the live store; run it with the compose stack up.
- "The new UI settings are missing" reports: verify the SERVED bundle first (grep the frontend container's output for the new symbol) before debugging code — the usual cause is a cached browser bundle or the user looking in the wrong place (settings live inside the campaign detail form, not on the campaign list); then have the user hard-refresh.
- **Alembic `server_default` with a SQL expression must be wrapped in `sa.text()`** (e.g. `server_default=sa.text("'{}'::json")`) — a plain string is sent by asyncpg as a bound parameter, so expression defaults like `'{}'::json` fail the migration with invalid-json, while the same code works on psycopg. When a migration fails on the live stack, run `docker compose exec api ... alembic upgrade head` again after fixing and confirm the version table advanced.

## Production deploy (button workflow; `docs/lowbid-cicd.md` in-repo is the source of truth)

- User's standing flow: merged PR → deploy IMMEDIATELY in the same turn ("деплой сразу после мержа"). `gh workflow run cd.yaml --ref main`, then poll `gh run view <run-id> --json status,conclusion` in a loop (foreground sleep-loops >600s auto-promote to a tracked background process — fine, the notification arrives on its own; deploy takes ~2–5 min).
- Prod smoke over SSH (`dlgrv@135.106.162.15`, key `~/.ssh/id_ed25519_lowbid`) — **`/docs` returning 404 is EXPECTED in prod** (`APP_ENV=prod` hides it; do not 'fix' it): probe API liveness with `curl -X POST http://127.0.0.1:8000/api/auth/login -H 'Content-Type: application/json' -d '{}'` → 422 = endpoint alive; nginx `/` → 302 = auth redirect working; `ls /var/www/lowbid/dist/index.html`; `systemctl is-active lowbid_api lowbid_bid_worker lowbid_playback_worker@1 lowbid_playback_worker@2` + both timers.
- Prod `.env` and DB survive every deploy (workflow backs up and restores them) — prod credentials are NOT the local dev ones; the local password-reset recipe never touches prod.
- **Small post-merge hotfixes go direct to main** on the user's explicit "пуш и деплой": commit `fix(lowbid-NN): ...` → `git push origin main` → wait for CI on main → `gh workflow run cd.yaml --ref main` → poll run → SSH smoke (`curl` login page 200 + `systemctl is-active lowbid_api lowbid_bid_worker`). The PR route stays the default for feature waves; direct push is the user's call, never a default.
- Restart logic in deploy scripts must enumerate instantiated systemd units explicitly: `systemctl list-unit-files --state=enabled` lists only the TEMPLATE of a template unit (status `indirect`), so running instances `@1/2` are invisible and a match-based restart branch silently no-ops on them. Match with `systemctl list-units --all '<name>@*'` or restart the explicit instance list — then verify fresh `ActiveEnterTimestamp` per instance, per the standing post-deploy rule.
- New behavior ships behind a global env flag defaulting OFF in prod (e.g. profile leases: absent `PROFILE_LEASE_ENABLED` = disabled), so a deploy never changes live traffic by itself — enabling is a separate explicit step the user controls.
- **Enabling a shipped-but-off behavior on prod: FIRST on a low-rate campaign, never the main 60k/min one** (23.10 case: `profile_lease_enabled=true` flipped via SQL on the main campaign exposed a fill-cycle window — entries from `top_up` reach the profile free-set only on the NEXT fill, up to `fill_interval` (200s) — attempts hitting fresh IPs failed with `PreferredIpUnavailableError` until the retry). Same seam class as error_gate and the bytes bug: components syncing through Redis at fill cadence; unit tests mock the neighbour and never see the window. Cover with a REAL `_fill_one_pool` cycle → immediate `acquire` integration test. Also compute the **quota budget BEFORE flipping the flag**: lease capacity = pool_count × profiles_per_ip × shows_per_profile_hour must exceed the campaign's target rps — on the 60k/min campaign it was ~9× short, so a fraction of lease attempts was guaranteed to fail closed regardless of code correctness. See `references/proxy-fill-lease.md` → Storm triage. Applying the GLOBAL env flag is a separate step from the per-campaign toggle: append to prod `backend/.env`, restart only the long-running workers that load settings at startup (`systemctl restart lowbid_bid_worker`, verify a FRESH `ActiveEnterTimestamp`); timer-driven oneshots (`lowbid_proxies_pool_worker`) read env per run — a restart between ticks is a silent no-op, and 'inactive' status there is normal, not a failed restart. After enabling, monitor 30+ min before calling it success — see `references/proxy-fill-lease.md` → Quota sizing.
- **Campaign settings on prod go through the API, not raw SQL UPDATE** — validation gates, audit trail, and no chance of writing a malformed JSON blob. **No working admin password is not a reason to fall back to SQL** — mint a scoped API token instead: INSERT into `api_tokens` (user_id, name, `token_hash` = sha256 of the plaintext, `prefix`) via the box's own psql, then `curl -H "Authorization: Bearer <plaintext>"` against the settings route; the PATCH passes the same validation as for a human, and the token revokes from the UI afterwards. Keep the plaintext only inside the one ssh+curl script, never in chat or logs.
- After a subagent code wave, run the commit gates YOURSELF before committing: `cd backend && uv run black app/` + fix any F401 it leaves — black/flake8 pre-commit hooks reject the commit, and a rejected hook aborts a chained `commit && push && gh workflow run` mid-chain with the earlier steps already done. Push rejected «fetch first» = a PR merged concurrently: `git fetch && git rebase origin/main`, then push and only then trigger CD.
- **Before pushing, run the exact CI lint commands over the FULL tree** (`uv run flake8 && uv run black --check .`, not just the files you touched) — subagent waves drop helper/repro scripts under `backend/scripts/` that CI lints even when the pre-commit run didn't; a lint-only CI failure after push wastes a full check+CD cycle. Fix what it catches (unused imports, F541) in the same push.
- **Prod incident: if an error storm CONTINUES after reverting the suspect commit, the trigger is config/data, not code** — a flag flipped via SQL lives in the DB and survives any revert; kill it at the data layer first (update the campaign setting, restart the worker, verify the storm rate → 0), then root-cause calmly. Also: storm ONSET can lag the trigger by ~a pool turnover (warmup), so correlate timelines before naming the cause — the revert that «didn't help» may simply predate the storm.
- **Prod rollback → re-land pattern**: `git revert --no-edit <sha>` for immediate relief, ship the root-cause fix as a new commit, then `git revert --no-edit <revert-sha>` to reapply — keeps history honest without cherry-pick conflicts. Any subagent-written test/script files that rode along must pass the full CI lints before the reapply push (see above).
- **A hand-written prod UPDATE is not applied until re-SELECT proves it** — check the column type before casting (a `::jsonb` cast on a `json` column mismatches silently: the statement runs, the value stays old), and never trust «UPDATE ran» as «setting changed».

## Prod data verification («проверь, всё ли правильно считается»)

Pipeline order — check freshness end-to-end before trusting any aggregate: ClickHouse events by day (is anything arriving at all?) → gateway request log (bids vs tracking pixels separately) → pacer worker logs (playback completions, UMG/SSP 429 shaping) → PG aggregates per campaign. A gap in step 1 with live bids in step 2 means traffic is going around the pipeline (demand disabled, campaign paused, or a partner fed directly), not that counting broke.

- Prod DB: `export PGPASSWORD=$(grep '^DB_PASSWORD=' ~/krutilka/backend/.env); psql -h 127.0.0.1 -U lowbid_user -d lowbid_db` on the prod box. Never put the raw password anywhere but that expansion.
- **When imp/start ratios collapse, check the IP limiter first**: the `/imp` endpoint silently drops pixels once a source IP exhausts its daily quota (`ipimp:{ip}:{day}` Redis key) while `/start` is not limited — starts keep flowing and impressions vanish with zero errors anywhere. A sudden drop to <5% imp per start in one hour's bucket is this limiter, not playback breakage.
- **Never write psql over `ssh host 'psql -c "..."'` inline** — the remote shell eats the double quotes and Postgres misreads quoted literals (`date_trunc('day',…)` turns into a column lookup). Write the SQL to a local /tmp script, `scp` it over, run `ssh host 'bash /tmp/x.sh'`.
- Buffer batch sizes are .env-tunable via `settings.buffer` (dataclass `Buffer` in `backend/settings.py`: `BID_BUFFER_BATCH_SIZE`, `BID_BUFFER_FLUSH_INTERVAL_SECONDS`, `PLAYBACK_STAT_BATCH_SIZE`, `BID_STAT_MAX_BATCH_SIZE`, … — defaults 2000 rows / 5s, wired through `_build_*_buffer` in `worker_settings.py`). They do NOT drive worker RAM: each flush is at most a few hundred rows, so "increase the chunk" never fixes memory; multi-day worker RSS growth is session accumulation, fixed by a worker restart (brief playback interruption). High worker RAM is by design per the user — don't propose shrinking it.
- **`bid_attempts` is write-only diagnostics: no API handler ever SELECTs it.** Full error analytics already live in `bid_stats` (`bid_stat_buffer.py`: every attempt of any status aggregates into (campaign, 5s bucket, status, error_type) counters incl. 429s) — so dropping raw ERROR rows from `bid_attempts` loses zero analytics. Implemented per `.hermes/plans/2026-10-22_buffer-reliability.md`: requeue-instead-of-drop in `BaseAsyncBuffer` (K=10 retry cycles → drop + `dropped_rows`), .env chunk sizes, `BID_ERROR_RAW_MODE=off|first_seen|all` gate (Redis `SET bid_err_seen:{campaign}:{cls}:{status} NX EX`, Redis failure fails open to `all`), and WIN-xml first_seen thinning (`win_xml_seen:{campaign_id} NX EX 3600`; non-first WIN rows store `[{"sha256":…,"len":…}]` instead of bodies; `BID_WIN_XML_MODE=full` restores bodies without a deploy). Defaults are `first_seen` — quote prod behavior only after checking the prod `.env`.
- **Buffer internals (verified against code — re-check file:line before relying on it):** `_to_row`/`_prepare` in `base_postgres_buffer.py` are SYNC and run inside the flusher task, not the bid hot path; retry cycles (`max_retry_cycles`, default 10) re-run the whole `_flush`→`_prepare` on the requeued batch, so any per-row gate or transform inside the flush path MUST be idempotent or computed once upstream (the proven pattern: decide in async `add()`/executor and store a flag on the buffered entry — e.g. `keep_full_xml` set once in `BidAttemptBuffer.add()`, only read by `_to_row`). `error_type` is `type(error).__name__` and `http_status` is set once on the error/outcome at creation — never parse error text per attempt; `bid_attempts` has no `created_at` — filter by `started_at`.
- **`backend/tests/fake_redis.py` is a hand-rolled double** (hash ops plus `set(nx=, ex=)`/`get`/`exists`/`delete` added for the NX-gate tests) — extend it for any new Redis op BEFORE writing gate/TTL tests; `fakeredis` is not in requirements-dev.
- **Integration tests must build Redis clients the way prod does (arq pool, NO `decode_responses`) — prod returns `bytes` values, and a test-built client with `decode_responses=True` never exercises the bytes path.** Real failure: a profile parser silently degraded a bytes payload to a CLEAN verdict (fail-open) while the suite stayed green on its decoded double. Boundary decoders must normalize bytes→str explicitly and reject unknown payloads loudly, never fall through to the benign default. Mind the repo's asymmetry: the store helpers normalize KEYS (`_key_str`) but NOT values — write tests against the real contract (str keys, bytes values); a mock that normalizes both sides stays green while prod bytes payloads hit the unnormalizing path.
- **Kuma push-monitors on the prod box must be added in TWO places**: the live `/etc/cron.d/kuma-push` AND the repo template `lowbid-ssp/deploy/server/cron.kuma-push` — `check-drift.sh` diffs the live file against the template and alerts on divergence. Monitors are single-level up/down (warn+crit = two monitors or msg-with-percent).
- **`etc/*.service` carry `TimeoutStopSec=150`, sized to the 60s buffer-drain stop budget** — keep the unit value in sync whenever graceful shutdown gets longer, or systemd SIGKILLs mid-drain and loses exactly the data the change protects. **CD does not install unit files**: changed `etc/*.service` must be copied to the box + `systemctl daemon-reload` by hand at deploy time, or the new stop budget silently stays the old one. Check restarts for «Killing»/exit 137 in journalctl.

- **Background probe scripts on the prod box: kill → launch → verify as SEPARATE small ssh calls, never one chained command.** A compound `ssh host 'pkill …; launch; verify'` that dies at connect exits 255 with zero output and you cannot tell which stage ran — check state after each stage (`pgrep -f` + `tail` the log) instead of trusting the chain. An immediate retry of a 255-empty ssh usually connects fine.
- **`pkill -f <pattern>` inside an ssh remote command kills the ssh session itself when the pattern occurs in its own cmdline** (the remote shell running pkill carries the pattern text) — session drops mid-chain, later stages never run. Use the bracket trick `pkill -f "[s]cript"` so the literal in the cmdline can't match.
- **soax_v2 proxy username format is `{PROXY_USERNAME}-{session_id}`** — the session suffix is MANDATORY (no suffix → `CONNECT tunnel failed, response 400`) and session ids must be short alphanumeric (`exp$(date +%H%M%S)` works; 17-char `hermes-<epoch>` fails). Verify the format with ONE foreground curl before burning time on a background probe that logs FAILs every minute.
- **soax sticky-session exit IP is stable only under CONTINUOUS traffic**: ~10s request intervals hold the same exit IP for minutes (even across processes); after ~60s idle the next request gets a NEW exit IP. A 60s-cadence probe therefore measures rotation, not stickiness — measure at the intended request cadence before designing IP-stable personas. Multi-day stable exit IPs are NOT achievable on soax; the antifraud bench plan must not assume them.

## Prod disk & retention

- Retention is cron/pg_cron, not scripts, but the WINDOWS DRIFT — read the live definition before quoting one (bid_attempts is currently 48h, tightened from 7 days; ad_playback_stats 30, bid_stats 60). Verify it works via `min(started_at)` age < window and `n_dead_tup` in pg_stat — not by assuming.
- **VACUUM never returns disk to the OS**: after a traffic spike the table files (especially jsonb TOAST on bid_attempts — tens of GB) stay at peak size forever; deleting rows reuses space internally but `df` never shrinks. Real reclaim = `pg_repack`/`VACUUM FULL` in a maintenance window; before promising disk savings, compute `pg_total_relation_size` minus heap+indexes to expose the TOAST bloat. Order matters: DELETE-purge first, THEN `VACUUM FULL` (it rewrites the whole table — ~4 min for ~9 GB under ACCESS EXCLUSIVE). **The prod deploy account has no passwordless sudo, and PG tables are owned by `postgres`** (`lowbid_user` is neither superuser nor owner): compression ALTERs, owner-level DDL and `journalctl --vacuum-size` are USER-RUN steps — check `sudo -n -l` and the table owner before planning them yourself, and hand the user ONE paste-block of exact sudo commands.
- Quick non-destructive disk wins on the prod box: `docker image prune -a -f --filter until=…` (several GB of dangling images) and a journald cap (`SystemMaxUse=` in `/etc/systemd/journald.conf` + restart; the journal alone can hold GBs). Both are system changes — list the plan and get the user's «да» first.
