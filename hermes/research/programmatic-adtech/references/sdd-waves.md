# Executing the plan via subagent waves (SDD)

Depth reference for `programmatic-adtech`: the controller protocol for implementing a plan through subagent waves in the lowbid/krutilka/lowbid-ssp repos.

- Use `subagent-driven-development` (in ~/.agents/skills) as the controller skeleton: implementer per task → task-review after each → final whole-branch review + verification-before-completion. Audit step first: for each task check (a) standalone dispatchability, (b) file-overlap conflicts, (c) natural TDD cycle.
- ONE SUBAGENT PER TASK, never per week/milestone: delegating a whole week to one agent silently drops the per-task review gates and the user will catch it. Split the plan so each dispatch = one task with its own verification criterion; after a parallel batch lands, run a cross-task integration sweep (build all + one end-to-end test through the joined parts) before the whole-batch review.
- Two-stage review protocol per task: (1) spec-compliance reviewer — read-only, runs the build/test/lint gates itself, verdict PASS/FAIL with findings as file:line + severity; (2) quality reviewer against the code standard. Fix rounds get ONE fixer agent applying the full findings list with a minimal-diff instruction; defer minor cleanup findings to a tracked backlog instead of inflating the fix round.
- Gate parallelism on FILE overlap, not task independence: tasks touching the same flow file run strictly sequentially in SEMANTIC order, not plan order — e.g. abandon-semantics (abandon fires NO error) must land before error-firing tasks that edit the same exception paths, or the exception-handling changes conflict.
- Narrow each task's scope to existing infrastructure: if it depends on a component from a deferred task (e.g. media fetcher → media error codes), keep only the implementable part and mark the rest TODO — never let an implementer stub half a subsystem.
- To run tasks in PARALLEL that share components, define the seam as an interface and paste its exact signature into EVERY related agent's context (each programs against the interface, fakes in tests); otherwise agents invent incompatible stubs and the merge conflicts. E.g. parallel decision-module and VAST-endpoint tasks both get 'program against `Selector.Select(ctx, req)`; the real implementation is another agent's job — use a fake in tests'.
- Stochastic/behavioral tasks need seed-fixation and range asserts over N runs (e.g. completion 60–85% over 200 runs), never exact values; use tdd-red-phase-pitfalls for distribution-assert pitfalls.
- Parallel implementers must NOT share one repo checkout even on disjoint branches — concurrent branch surgery in one worktree corrupted branch topology, and a repeat with a 'disjoint' backend-fix/frontend-feature pair had the fixer commit onto the frontend's parallel branch and repair it with fast-forward ref surgery. 'Disjoint files' is NOT disjoint enough: both agents create branches from the same base in the same worktree, so the second `git checkout -b` lands on whatever HEAD the first left. Sequence file-overlapping tasks (rule above) AND give genuinely parallel tasks separate `git worktree`s; prefer a linear stacked-branch chain (each task branches off the previous task's tip) — it makes the final gate a simple `git log <base>..HEAD` integrity check plus whole-stack review.
- A money-reserving decorator (Reserve inside Decide) shifts rollback duty to the CALLER: every post-decide reject path in the handler (floor filter, build/marshal failure, timeout) must Rollback, or each rejected request silently spends the campaign's budget. When adding such a decorator, audit all downstream reject paths at the same time and add a leak test ('budget equals full limit after a rejected request').
- PASS reviews still gate on severity: a verdict of PASS with a money-affecting finding means dispatch an immediate fix round — only truly cosmetic findings go to the cleanup backlog.
- Revert tasks must restore the BASE behavior of every path they touch, not just delete 'our' additions: after reverting, diff the touched files against the base commit and confirm every residual line belongs to a live feature, grep the removed symbols to zero occurrences, and check that nothing pre-existing died together with our feature — a shared code path (an interrupt/branch inside the same function) goes out with the addition, silently changing behavior relative to base.
- Gate a config knob by its BEHAVIORAL effect, not its plumbing: a test asserting the getter/storage returns the value passes while the mechanism is dead (value accepted by API+UI, no code acts on it). The closing test must observe the effect — override probability to 100% → the event actually fires; 0 → never — and a revert review must include one such effect test for every knob in the reverted code.
- When an aggregate verification target exists (`make test-integration` etc.), adding a new package REQUIRES adding it to the target — the new package's tests then never run in the batch check and nobody notices.
- Give reviewers QUANTITATIVE invariants to reconcile, not 'check correctness': 'measured completion 74.9% vs theoretical 75.5% — explain the gap' surfaced a real edge-case bug (margin on short creatives) that generic review language missed. Also ask targeted edge questions (smallest creative, skipoffset=0, retry classification).
- The cross-task integration sweep must WIRE THE REAL CHAIN (real store → cache → selector → handler), not just `go build ./...`: parallel implementers each pass against their own fakes, so seam defects only surface when real components connect. Recurring seam-defect shapes to probe for: a list query not hydrating child rows (creatives) so the selector silently gets empty entities; a relation table (m2m zones) written but never read back; a handler not populating the request signals (geo/UA) the decision layer filters on; a component whose constructor demands a WIDER repo interface than the store actually implements (narrow the consumer-side interface instead); a JSON-tag mismatch between producer and consumer across a queue (producer marshals `ip_hash`, consumer struct decodes `ip`) — the field is silently dropped end-to-end while both sides' unit tests stay green.
- Reviewers must audit test ASSERTS, not test existence: a test whose asserts cover less than the property under test (an idempotency test that checks only zones, not campaigns) masks the exact bug it claims to guard — fix the test in the same round as the bug, and extend the e2e test to exercise the property against the real backing service (re-run the seed against live PG).
- Test fixtures must set explicitly every field the code discriminates on (e.g. zone status): zero-value defaults silently rely on lenient handlers, and the whole fixture set falls over the moment the check is added — hiding that the production data path may also carry unset values.
- When production code gains a call on a collaborator (e.g. a registry grows a new store accessor), grep the test tree for `MagicMock(spec=<that class>)` BEFORE running the suite and give the new method explicit AsyncMock stubs — a spec'd mock auto-creates a plain child MagicMock for the new attribute, so the seam call returns a mock instead of a coroutine and only the old seam tests fail, in files nobody edited in this task.
- Verify 'configurable via X' claims end-to-end: a pydantic Literal-keyed API model silently drops dict keys it doesn't know, so a defaults key absent from the schema is unreachable no matter what the docstring says. Same failure shape when EXTENDING a saved config with a new section: adding a flow-side read of `event_configs['error']` does nothing while the PATCH model's `PlaybackEventConfigs` is a Literal-keyed model — a pydantic `extra=ignore` drops the unknown key on validation, so the PATCH round-trip ERASES the setting the flow already knows how to read. Fix the API model first (`PlaybackErrorEventConfig(fire_chance: Field(ge=0, le=100))` + model field `error: Field(default_factory=...)`), and add the new key to the Literal/`expected_event_names()` set — a future validation pass keyed off that set would silently drop the section again.
- JSON columns need no migration for new config keys: `event_configs` is an untyped JSON column, so a new section just serializes along; test the round-trip (PATCH model → `model_dump(mode=json)` → json round-trip → `model_validate`) and the legacy row (stored JSON without the new section deserializes with the field default), not the DDL.
- Distribution stats that live on flow STEPS are per-step-instance: VastFlow builds each step as a separate object, so a counter dict on `AdPlaybackStep` is invisible to `PreparePlaybackPlanStep` (wrapper-fetch failures fire error pixels there) — inject ONE shared stats dict into every step at flow build time (constructor DI by param name, NOT through the serializable plan entity), and put the log line wherever the path exits (a step that re-raises never reaches another step's finally).
- Frontend e2e with a Playwright webServer can time out on infra (IPv6/IPv4 localhost bind mismatch: Vite binds ::1, config probes 127.0.0.1), not on code — before diagnosing code, try `PLAYWRIGHT_BASE_URL` against an already-running dev server; and confirm suspicious spec failures are pre-existing by `git stash`-ing the changes and re-running on the base.
- API client change needs NO plumbing when it serializes a whole typed map: the frontend PATCH sends `event_configs` as one typed JSON object, so a new backend field arrives by updating ONLY the TS type + defaults + panel input + validation + help text — do not hunt for a field list that doesn't exist. But check every CLONE/normalize helper: a clone that rebuilds the map field-by-field silently drops the new section when a saved config is loaded into the edit form.
- Review-loop resume discipline: see the always-on rule in SKILL.md (check repo state first on interruption, resume from the live transcript instead of restarting; no `{name}`-style brace placeholders in dispatched goals).
