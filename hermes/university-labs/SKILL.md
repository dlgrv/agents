# Университетские лабораторные работы

Контекст: Moodle-курсы универа (напр. «Нейронные сети», преподаватель Иванов К.О.), студент Долгирев Л.М., группа ИТС-41з. Лабы лежат в `~/university/<Курс>/<ЛРN>/`.

## Порядок работы

1. Прочитать методичку целиком до начала — там все задания, контрольные вопросы и требования к отчёту. Ссылка в Moodle может вести на Google Drive, а файл оказаться не PDF, а JSON ноутбука Colab: после скачивания проверять `file` — если контент начинается с `{"cells":`, парсить `json.load` и собирать текст из `source` ячеек (markdown = задания и вопросы, code = скелет решения). Скачивание Drive-файла: `curl -sc /tmp/gc 'https://drive.google.com/uc?export=download&id=ID'` → вытащить `confirm`/`uuid` из формы → повторный curl с ними (без этого приходит страница проверки или обрезанный файл).
2. Скрипты: по одному на задание, номер задания в имени файла, имена .py — **латиницей** (`task1-create-db.py`), не кириллицей. Каждый скрипт запустить и проверить вывод до сдачи.
3. Отчёт — docx по ГОСТ: Times New Roman 14, полуторный интервал, отступ первой строки 1,25 см, поля 30/10/20/20 мм. Имя файла `ЛРN_Долгирев_ИТС-41з.docx`.
4. Сдача: формат вложений в задании/методичке часто вообще не указан — по умолчанию один docx-отчёт; когда сдаётся комплект (отчёт + ноутбук + данные), прикреплять каждый файл отдельно — Moodle принимает до 20 файлов по 128Мб, zip не обязателен. Наполнение комплекта согласовать с юзером (docx / ipynb / данные) перед загрузкой. Загрузка файлов в Moodle — прикреплять к ответу на задание внутри курса.
5. Упаковка: все файлы лабы в одну папку `ЛРN_Долгирев_ИТС-41з/`, рядом zip с тем же именем.
6. Если сдаёшь .ipynb вместе с docx: в ноутбуке только код и краткие пометки — markdown-ячейки не должны дублировать текст отчёта (преподаватель читает отчёт, дубль в ноутбуке = расхождение версий). Текст markdown-ячеек тоже прогнать по чек-листу ИИ-паттернов.
7. Выполнение лабы сопровождать пошаговыми объяснениями простым русским: аналогии «на пальцах», таблицы параметров, числа (юзер учится в процессе — «объясняй как 5-летнему»), а не только готовыми файлами.

## Вход в Moodle
Работать через изолированный браузер (`browser.use_real_profile false` — уже установлено в конфиге; креды ВолгГТУ в vault). Не просить юзера менять дефолтный браузер или закрывать Chrome.

`elearning.volgatech.net` редиректит на `auth.volgatech.net` (Trusted.ID): логин вписать самому, пароль — только через browser_vault_fill, затем нажать кнопку «ВОЙТИ» (искать по тексту кнопки, у неё нет type=submit). После входа: страница курса → задание → блок «Материалы» содержит ссылки на методичку.

**Отметить посещение всех курсов (преподаватель видит lastaccess и кто ни разу не заходил):** получить список своих курсов через webservice (см. ниже) и goto каждой страницы курса с полной загрузкой — сам факт загрузки страницы курса пишет `lastaccess` и событие в журнал; этого достаточно, ничего кликать внутри не нужно.

**Поиск своего курса — через Moodle webservice, не через DOM.** Карточки курсов на /my/ рендерятся JS-ом и не находятся querySelector'ом. Надёжный способ: с любой страницы портала взять `M.cfg.sesskey` и POST'ом на `/lib/ajax/service.php?sesskey=...` вызвать `core_course_get_enrolled_courses_by_timeline_classification` (classification: 'all') — вернёт id и fullname всех своих курсов. Поиск по слову через `course/search.php?q=` может быть пуст. Скачивание resource-файлов (методички, задания): resource/view.php?id=N иногда редиректит на курс — кликать по ссылке со страницы курса (тогда файл падает в ~/Downloads), потом копировать в папку курса с внятным именем.

## Правила отчёта docx

- В docx — **только ответы на контрольные вопросы**: шапка (название лабы, «Выполнил», «Проверил») + вопросы с ответами. Без цели, схемы БД, хода работы с кодом, вывода — код и выводы живут в .py-файлах. Расширять отчёт разделами только по явной просьбе.
- Упоминания имён .py-файлов внутри docx держать синхронными с реальными именами: переименовал файл — замени упоминания в docx (замена по runs через python-docx).

## Отчёты по производственной практике

Комплект — Титульный лист, Дневник практики, Аттестационный лист, Основная часть (~30 стр.). Папка `/Users/dlgrv/university/<Суть> (<Фамилия И.О.>)` — файлы класть туда (и синхронизировать копию в Downloads, если она уже заведена). Пример оформления — файлы одногруппницы в Downloads.

Порядок:
1. Оформление извлекать из образца программно (`docx_read.py --styles` + margins section'а), не из лабораторных дефолтов — у отчёта по практике поля 30/**15**/20/20 мм, а не лабораторные 30/10/20/20.
2. Дневник и аттестационный лист заполнять в **официальный бланк вуза** через python-docx по индексам ячеек; перед заполнением прочитать таблицы бланка и сверить индексы (они неочевидны, например «Вид практики» может быть ячейкой 12, а не 8). Не собирать таблицы с нуля — структуру бланка сверяет деканат.
3. В бланке может не хватать таблицы индивидуального задания — вставлять недостающее текстом после заголовка, не перекраивая бланк.
4. Основную часть писать по структуре образца (ВВЕДЕНИЕ → Перечень сокращений → Аннотация → разделы → Полученные навыки → Заключение → Источники), каждый H1 — с новой страницы. Фактуру по предприятию (история филиала, даты, технологии) добывать web_search'ем, а не выдумывать.
5. Внутритекстовые ссылки `[N]` на источники обязательны (ГОСТ 7.0.5) — проверять их наличие после написания.
6. Содержание (поле TOC) по ГОСТ положено, даже если в образце его нет — добавить и предупредить юзера, что если эталон кафедры без содержания, страницу легко удалить.

### Переработка отчёта в «вариант 2» (перефраз той же работы)
Когда юзер просит переработать существующий отчёт — та же концепция и фактура, но другая структура и формулировки:
1. Сохранять в НОВЫЙ файл «<имя> (вариант 2).docx» рядом с оригиналом — оригинал не трогать.
2. Структуру перестроить: слить/раздробить/переименовать разделы (число подразделов менять на ±1), старые заголовки не должны остаться ни в одном. Таблицы, листинги кода, список источников и сокращения не переписывать — это фактура, она по смыслу одинакова.
3. Текст заменять по индексам абзацев python-docx (замена по runs), исходник структуры выгрузить с индексами в /tmp-скрипт перед правкой.
4. Графики заменить на новые ДРУГОГО типа (в оригинале линии → в новом area/hist/bar), сгенерировать matplotlib'ом и подменить media в docx; можно добавить один новый рисунок с подписью по ГОСТ («Рисунок N.M — ...»). Кривые — правдоподобные: ночной минимум, дневное плато, вечерний пик.
5. Финальная проверка собранного файла: старых заголовков нет, новые на месте, все подписи рисунков подряд, число картинок совпадает с ожидаемым, в тексте нет мусорных символов (`re.findall(r"[\u4e00-\u9fff]", full)` пуст — при bulk-заменах в скрипт затесываются артефакты), плотность тире не выше оригинала (посчитать в обоих, вне списка сокращений; избыток проредить заменой на двоеточия/запятые), чек-лист ИИ-паттернов.

### Питфоллы
- **TOC собирает только стили Heading 1/2** — обычные bold-абзацы в поле не попадут. Назначить `Heading 1/2`, потом вернуть вид (TNR 14, капс, по центру, чёрный) — Heading-стиль несёт своё форматирование. Word строит содержание только по «Обновить поле»: плейсхолдер виден до этого, а статистику страниц читать после.
- **Вставляя несколько абзацев перед якорем, делать addprevious в прямом порядке по одному** — каждый встаёт непосредственно перед якорем и итоговый порядок правильный; связка `reversed()` + перенос элементов между деревьями даёт обратный порядок. После структурных вставок проверять первые абзацы через `docx_read.py --text`.
- **Число страниц считать AppleScript'ом в Microsoft Word** — python-docx страницы не считает. `open (POSIX file "...") as text`, `delay 5`, затем `compute statistics of document 1 statistic statistic pages` (и `statistic words`); закрывать `saving no`. Запросы `text of document`/`paragraph i of document` могут возвращать пустоту и ломать скрипт — контент читать через `docx_read.py`, AppleScript использовать только для statistics; `save as ... format PDF` у Word может не работать.
- **docx_edit.py может зависать на тяжёлых файлах с картинками** — если CLI-замена не отвечает, делать ту же правку скриптом python-docx напрямую (replace по runs) и проверять результат `--text`.
- `[0]` в тексте — не обязательно битая ссылка на источник — это может быть `capture_output` из листинга кода; проверять контекст находки перед «исправлением».

## Определить предмет по скачанному архиву
Когда юзер скидывает архив чужой/своей работы без контекста («это какая-то моя работа»):
1. `unzip` в `/tmp/<имя>/`, `find . -type f` — расширения сразу сужают предмет (.PcbDoc/.SchDoc/.PcbLib = Altium = конструирование/технология ЭС; .ipynb = ML/ИИ и т.п.).
2. docx-файлы часто содержат только строку-титул («ЛР4. Вариант 2А») — предмета не дают. Идти в PDF: `pypdf` первой страницы достаточно — в штампе чертежа фамилия преподавателя («Проверил»), обозначение документа (ПГТУ.xxx), тема и формат листа. Метаданные PDF (`reader.metadata`) часто дают больше текста: `/Creator` называет программу-источник (КОМПАС-3D = схема/чертёж, сразу видно чем рисовали), `/Designation` — шифр ЕСКД (вида КНФУ.XXXXX.00N Э2), `/Name` — название документа. `extract_text()` векторной схемы вытаскивает позиционные обозначения (DD1…), типы микросхем и подписи без конвертации в картинку. Превью PDF в PNG без pdftoppm: `qlmanage -t -s 1600 -o /tmp файл.pdf` → `/tmp/файл.pdf.png`.
3. Найденный предмет сопоставить с папками в `~/university/` и чек-листом `задания-на-сессию.md`; переименовать по формуле (см. «Именование файлов») и положить в папку предмета. Спросить юзера только если предмет по содержимому неоднозначен.

## HTML-шпаргалка к защите
Шпаргалки для чтения с телефона делать в HTML (один файл, рядом с .md): липкое меню с якорями по лабам сверху, заголовки лаб — контрастные плашки (находить глазами при скролле), таблицы сжимаются под узкий экран, **только светлая тема** (без prefers-color-scheme: dark). Содержимое 1-в-1 из markdown. Генерировать скриптом `scripts/make_shpargalka_html.py` (`python3 make_shpargalka_html.py <шпаргалка.md>` — сам ставит якоря по h1 «ЛР<N>»). **.md — источник истины: после любого расширения текста шпаргалки перегенерировать HTML**, иначе на телефоне останется старая версия.

## Питфоллы

- **Выполнять .ipynb через nbformat ExecutePreprocessor, а не `jupyter nbconvert --execute` из CLI** — CLI-прогон может упасть на matplotlib-ошибке категориальных данных («'value' must be an instance of str or bytes, not a float»), тогда как тот же ноутбук через `nbformat.read` + `ExecutePreprocessor(timeout=600).preprocess(nb, {'metadata': {'path': '.'}})` проходит целиком; CLI при ошибке ещё и не сохраняет частичный прогресс в inplace-режиме. Python-окружение для выполнения — `~/jupyter_env/bin/python3` (numpy, sklearn, matplotlib, pandas, seaborn уже поставлены; недостающие пакеты доставлять pip'ом туда же).
- **Загрузка файлов в Moodle через браузер: на странице ответа нет `input[type=file]`** — открывать пикер кликом по `.fp-btn-add` в тулбаре filemanager, в пикере появится `input[name=repo_upload_file]`; файл вписывать через CDP и подтверждать кликом по `.fp-upload-btn`, повторять на каждый файл (после каждого «Добавить» пикер пересоздаёт input — **перед каждым setFileInputFiles заново** `DOM.getDocument` → `DOM.querySelector("input[name='repo_upload_file']")`; stale nodeId даёт «Node is not a file input element» даже если js()-querySelector input видит).
- **У большинства заданий нет кнопки «Отправить на проверку»** — сохраняющая кнопка называется просто «Сохранить» (ищи по `/Сохранить/`, не по «Сохранить изменения»), после неё статус «Ответы для оценки» и есть сдано (так настроил преподаватель); не тратить время на поиск кнопки отправки, проверять статус и список файлов в «Ответ в виде файла». Если статус «Не оценено» и доступна кнопка «Редактировать ответ» — файл ещё можно заменить.
- **Статус сдачи курса проверять по assign- и quiz-страницам**: у каждого `mod/assign/view.php?id=N` читать блок «Состояние ответа» (попытка, файл, дата) — этого достаточно для чек-листа; у `mod/quiz/view.php?id=N` — «Разрешено попыток» и факт «Тестирование закончено» (нет строки о попытке = тест не пройден).
- **zip пересобирать последним, после всех правок файлов** — архив не обновляется сам, устаревший zip незаметно уедет в сдачу.
- python-docx недоступен в execute_code-sandbox — работать с docx через `terminal` системным `python3`.
- **Старый `.doc` читать через `textutil -convert txt -stdout файл.doc`, не python-docx** — python-docx отвергает файлы с расширением .doc даже когда внутри OOXML-контейнер (content type не совпадает с ожидаемым). textutil сплющивает таблицы в поток строк — столбцы теряются, поэтому вывод «в таблице нет такого-то столбца» делать только после перепроверки другим способом.
- Русские имена файлов в zip: `unzip -l` показывает кракозябры — это норма листинга, не порча архива; проверять состав по количеству файлов.
- **Перед сдачей прогнать итоговый текст docx по чек-листу ИИ-паттернов** (файл `стиль-без-ии-паттернов.md` в университете): маркерные фразы, повторы одного союза в соседних предложениях («Кроме того, …» дважды подряд) и т.п. Проверять именно собранный текст отчёта, а не исходные материалы.
