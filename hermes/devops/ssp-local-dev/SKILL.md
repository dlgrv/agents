# Lowbid SSP (ortblabs/ssp) — ops и гоча

## Идентификация
- Репо: `ortblabs/ssp` (private), локально `~/aezly/lowbid-ssp`. Проды: https://ssp.lowbid.net (админка + VAST/RTB).
- Коммиты по конвенции `type(ssp-NN): desc` (skill lowbid-git-workflow).

## Деплой (как krutilka)
- CD: GitHub Actions `cd.yaml`, SSH-ключ `ssp_github_actions` → `deployer@135.106.162.15:/home/deployer/ssp` (аналог `deployer_github_actions` у krutilka). Secrets в репо заполнены.
- Цепочка: nginx (ssp.lowbid.net → 127.0.0.1:18080) → gateway-контейнер :8080. `deploy/docker-compose.vps.yaml` лежит В РЕПО (workflow распаковывает fresh-код и снесёт серверный override — не хранить его только на сервере).
- Триггер CD вручную: `gh workflow run cd.yaml --ref main -f branch=main`, статус через ~4.5 мин: `gh run view <run-id> --json status,conclusion`. Живость прода: `curl -X POST https://ssp.lowbid.net/rtb/1 -d '{}'` → 400 (валидация отвечает — сервер жив; голый `/rtb` теперь 404 — buyer-routing закрыл legacy).
- НЕ бандлить push + CD-триггер + sleep в один terminal-вызов: на запрос подтверждения не ответят за таймаут — отменится ВЕСЬ вызов, включая уже выполненные шаги. Сначала спросить юзера, потом push и триггер CD отдельными вызовами.
- Перед триггером CD убедиться, что коммит ФАКТИЧЕСКИ на main: merge мог пройти на ветке subagent'а — тогда push отвечает «Everything up-to-date», а CD уезжает со старым кодом. После merge проверить `git log --oneline -1` на main и что push реально двигал (`main -> <sha>`), и только потом `gh workflow run`.
- Имена веток со скобками/спецсимволами (`feat(ssp-20)`) — всегда в кавычках в git-командах, иначе merge падает «not something we can merge».
- **CD доставляет код, но долгоживущие процессы его не подхватывают.** Compose-сервисы SSP CD пересоздаёт, а systemd-воркеры krutilka (`lowbid_playback_worker@1/2`, `lowbid_bid_worker`, `lowbid_api`) — НЕТ: после «success» CD воркеры могут нести код месячной давности (парсер-фикс не действует до рестарта). После каждого деплоя: рестарт затронутых воркеров `ssh ssp-deploy 'sudo -n systemctl restart lowbid_playback_worker@1.service lowbid_playback_worker@2.service lowbid_bid_worker.service'`, затем верификация: свежий `ActiveEnterTimestamp` (`systemctl show <svc> -p ActiveEnterTimestamp`), 0 error/traceback в journalctl за пару минут, живой поток (например, рост пиксель-запросов в ssp-gateway логах). Рестарт системных сервисов — сторона, требующая подтверждения юзера (runtime-approval).

## КРИТИЧНО: go:embed
Gateway вшивает `frontend/dist` бинарём (`frontend/embed.go`). **Пересобирать gateway СТРОГО после сборки фронта**, иначе на проде/локально отдаётся старый бандл. Проверка: `curl localhost:8080 | grep -o 'assets/index-[^"]*.js'` vs `ls frontend/dist/assets/`.

## КРИТИЧНО: Kafka topic до деплоя
Consumer (franz-go) при отсутствующем topic МОЛЧА буферизует записи и сам его не создаёт — логи и метрики зелёные, событий в ClickHouse ноль. Каждый новый topic создавать ДО деплоя (внутрь kafka/redpanda-контейнера), а конвейер верифицировать фактом роста `SELECT count() FROM ssp.events` после живого трафика — «нет ошибок в логах» конвейер не доказывает.

## Сервер (135.106.162.15)
- SSH: `ssh -i ~/.ssh/id_ed25519_lowbid dlgrv@...`; **одна неудачная попытка = стоп** (fail2ban); серию мелких ssh-проверок батчить в ОДИН вызов — частые подключения сами по себе триггерят fail2ban даже без неверных попыток, а сессия админ-раунда легко набирает десятки коннектов. sudo через askpass: одноразовый хелпер на сервере — локально `PW=$(grep '^SUDO_PASSWORD=' ~/.hermes/.env | cut -d= -f2)`, `printf '#!/bin/sh\necho "%s"\n' "$PW" > ap2.secret && scp -i <key> ap2.secret dlgrv@<host>:ap2.sh && rm -f ap2.secret`; на сервере `chmod 700 ~/ap2.sh`, команды через `export SUDO_ASKPASS=$HOME/ap2.sh; sudo -A …`. Хелпер УДАЛЯТЬ после админ-раунда (`rm ~/ap2.sh`) и пересоздавать перед следующим — пароль не живёт на сервере постоянно.
- Для деплой-операций есть алиас **`ssp-deploy`** (юзер deployer, NOPASSWD `sudo -n systemctl` для lowbid_*-сервисов) — рестарты воркеров и read-only проверки (`docker ps/logs`, `systemctl show`, `journalctl`) ходить через него; путь с askpass остался для админ-задач под dlgrv.
- Админка на проде: авторизация сессионная (cookie, хэш в PG) — НЕ basic-auth; `ADMIN_INITIAL_*` в deploy/.env годятся только для бутстрапа пустой БД, реальный пароль из .env не восстановить. Живая проверка admin-API без сессии: 401 = роут жив и задеплоен, 404 = роута нет; фронт-раздел верифицировать grep'ом его текста по JS-бандлу с ssp.lowbid.net. Живая репродукция бага ЛК в изолированном браузере: вставить временного админа прямым INSERT в PG (логин уникальный, пароль — bcrypt-хэш, сгенеренный локально), удалить строку сразу после репро. Порядок триажа «у юзера пусто»: сначала сервер (API-ответ 200/500 + логи + прямой CH-запрос), потом клиент — не верить «сервер отвечает 200» без проверки ОТВЕТА НА ПОВТОРНЫЙ запрос (интермиттентный 500 ловится только повтором). Не тратить раунд на подбор basic-auth, которого нет.
- ClickHouse: у сервера нет IPv6 — healthcheck только `127.0.0.1` (не localhost → ::1), `listen_host=0.0.0.0`.
- Интермиттирующие 500 «internal error» на тяжёлых запросах статистики = сначала `docker logs ssp-clickhouse-1` на MEMORY_LIMIT_EXCEEDED. Типичная причина — `code: 241 MEMORY_LIMIT_EXCEEDED` + «OvercommitTracker»: ЭФФЕКТИВНЫЙ лимит CH = 90% cgroup mem_limit контейнера, и это лимит на СУММАРНЫЙ RSS сервера (кэши + параллельные запросы + baseline), не на один запрос. Лимиты править В РЕПО compose (хост 12G, avail ~7G) — не override'ом на сервере. Миграции/сиды — из контейнера, креды в `deploy/.env` на сервере.
- Рецепт тюнинга памяти CH под тяжёлую агрегацию: (1) фактический расход запроса смотреть в `system.query_log` (`memory_usage`, `query_duration_ms`, type=2) — не гадать по «would use» из ошибки (там RSS-бейзлайн приплюсован); (2) память агрегации кратна потокам — `SETTINGS max_threads = 2` в тексте запроса режет её кратно; (3) `max_bytes_before_external_group_by` (users.d) отдаёт агрегацию на диск, но НЕ покрывает read-буферы MergeTree — spill не панацея; (4) кэши CH по умолчанию НЕ ограничены: mark_cache раздувает RSS до общего лимита, и ЛЮБОЙ следующий запрос гибнет — ограничивать `mark_cache_size` в config.d; (5) mem_limit поднимать с оглядкой на хост (free -m), а не до бесконечности — сигнал, что пора агрегат, а не лимит.
- Агрегация по РАСТУЩЕЙ raw-таблице на лету не масштабируется: запрос, влезающий сегодня, гибнет через неделю роста. Правильная форма — rollup закрытых окон в отдельную таблицу (у статистики — `stats_daily`, тот же дедуп-паттерн argMax/uniqExactIf, числа идентичны raw-пути), live-путь только для «сегодня». Дизайн: PARTITION BY date = идемпотентный перезапрос окна (DROP PARTITION + INSERT); ленивый rollup со стороны читателя (нет строк за день → свернуть) не требует cron; мьютекс в процессе сериализует параллельные тики. Ловушки: (а) alias argMax-агрегата НЕЛЬЗЯ упоминать в GROUP BY (CH матчит алиас, а не сырую колонку — алиасы `*_dim`, GROUP BY по сырым); (б) колонка-измерение, осмысленная только у подмножества событий (err_code только у err), склеивает разные логические строки в одну группу — разделять сентинелом (`if(event='err', code, char(1))`); (в) rollup закрытого дня не подхватывает поздно доехавшие события — расхождение с внешней сверкой копеечное, но помнить при сверке с pacer.
- Gateway при старте должен ждать ВСЕ backing-сервисы через `depends_on: condition: service_healthy` — иначе wiring деградирует молча: gateway, стартовавший раньше CH, поднимается со `stats_enabled:false` и отдаёт мгновенные пустые 200 («Нет данных») без единой ошибки в логе. Рестарт CH (новый mem_limit/config) длится дольше старта gateway — после инфра-деплоя рестартовать gateway отдельно и проверять строку `admin api mounted` с `stats_enabled:true` в логах. Go-хендлер при ошибке запроса обязан логировать err (slog.Error) до writeError 500 — голый «internal error» без лога = час триажа. Миграции/сиды CH/PG — из контейнера, креды в `deploy/.env` на сервере.
- GeoIP за CF+nginx: реальный IP юзера — **последний** XFF-хоп / `CF-Connecting-IP` (nginx `$proxy_add_x_forwarded_for` ставит CF-IP первым).

### Диск и логи сервера (профилактика переполнения)
- Логи контейнеров ограничены В ДВУХ местах: якорь `x-logging` (json-file, `max-size: 50m`, `max-file: 3`) в базовом `deploy/docker-compose.yaml` для compose-сервисов И `/etc/docker/daemon.json` с теми же log-opts на сервере — daemon.json нужен для контейнеров ВНЕ compose (uptime-kuma, разовые). `systemctl reload docker` применяет дефолт только к НОВЫМ контейнерам — живые несут старые лимиты до пересоздания; проверять фактические лимиты `docker inspect <c> --format '{{.HostConfig.LogConfig.Config}}'`, а не `docker compose config`.
- Итог деплоя верифицировать фактическим состоянием контейнеров (`docker ps`, inspect), а не conclusion'ом CD-рана: ран может отрапортовать failure (healthcheck при перекате), при этом новая конфигурация уже применена — и наоборот.
- После переполнения диска проверять redis ДО следующего деплоя: запись, оборванная в момент «диск полон», бьёт хвост AOF — redis уходит в crash-loop «Bad file format reading the append only file», CD падает «container ssp-redis-1 is unhealthy», зависимые сервисы застывают в Created и сами не стартуют. Фикс: `docker run --rm -v /var/lib/docker/volumes/ssp_redisdata/_data:/data redis:7-alpine sh -c 'yes | redis-check-aof --fix /data/appendonlydir/appendonly.aof.<n>.incr.aof'` → `docker restart ssp-redis-1` → ВРУЧНУЮ `docker start` всем Created-контейнерам. `--fix` отрезает только битый хвост — безопасно.
- Логи воркеров krutilka/pacer — ТОЛЬКО journald (юниты `StandardOutput=journal`, ретеншн текстовых лог-файлов упразднён вместе с директорией). БД `bid_attempts` (host-PostgreSQL `lowbid_db`) — cron: `DELETE WHERE ts < now()-interval '7 days'` + VACUUM: jsonb-тела запросов/ответов раздували её до ~70 ГБ сверх heap при отсутствии retention.
- Логи SSP-контейнеров также дублируются в хост: gateway/consumer пишут syslog (`/var/log/lowbid-ssp/`, владелец dir `syslog:adm` — иначе rsyslog-юзер не создаст файл); файл-фильтр в rsyslog матчить по `$programname`, в heredoc экранировать `$` (иначе переменная съедается молча). Конфиги с `$var` (cron-файлы, rsyslog-фильтры) НЕ писать ssh-heredoc'ом вообще — генерить из репо-шаблона подстановкой секретов; если уж heredoc — сразу грепать результат на наличие `$` и реальных значений, пустая переменная в cron выглядит валидной строкой и молча шлёт в мониторинг пустоту. imjournal rate-limit отключён — с ним rsyslog теряет события после рестарта. Prometheus+grafana — в compose-профиле `monitoring` (не поднимаются прод-деплоем).
- systemd-юниты с `StandardOutput=file:/var/log/...` не стартуют, если каталог логов переименован/удалён (209/STDOUT, сервис молча не работает): при переносе лог-директорий править ВСЕ юниты, пишущие туда, разом и проверять `systemctl status` каждого — усыпивший юнит (например, наполнитель прокси-пула) валит каскад каскадной ошибкой (ProxyPoolEmptyError у playback), а не своей. **Юниты — источник истины В РЕПО** (`etc/*.service`): CD копирует их на сервер БЕЗУСЛОВНО при каждом деплое — ручная правка юнита по ssh переживёт только до следующего CD. Фиксы юнитов коммитить в репо; инвариант закреплять гейтом в CI (grep `/var/log` по `etc/*.service` роняет сборку). Юнит, добавляемый в CD, требует ТРИ вещи разом: (1) безусловный `cp` — ветка «только если файла нет» оставляет серверный sed-вариант навсегда, правки репо молча не доезжают; (2) per-file NOPASSWD-строку в `/etc/sudoers.d/deployer-systemd` (sudoers содержит точные `cp <src> <dst>` правила — без строки для нового юнита шаг падает «a password is required»); (3) `enable --now` вместо голого `start` — иначе сервис не переживёт ребут. После CD верифицировать СОДЕРЖИМОЕ файла в `/etc/systemd/system/` (`grep StandardOutput <unit>`), а не conclusion рана: ssh-heredoc без `set -e` возвращает exit-code ПОСЛЕДНЕЙ команды — упавший в середине sudo cp маскируется зелёным финалом. После оживления транспортного уровня проверять app-состояние, а не останавливаться: воркер может рапортовать «skipped: no enabled pools» — включённость пула это флаг в БД (`proxy_pools.enabled`), не состояние юнита.
- ВСЕ серверные конфиги (cron.d, rsyslog, logrotate, docker daemon.json, nginx, sudoers) — В РЕПО `deploy/server/` + идемпотентный `install.sh` (ставит только отсутствующее, добавляет drift-строку) и `check-drift.sh` по cron: сравнивает нормализованные копии сервер-файлов с репо-эталонами, при расхождении exit 1 + push в Kuma-монитор «Config drift» — правило «чинить в репо» закреплено автоматической детекцией, а не памятью. Нормализация диффа обязана игнорировать секреты (токены-плейсхолдеры в репо vs реальные на сервере) и комментарии (репо несёт документирующие строки). Секреты вне репо: `/etc/kuma-tokens.env` (root:root 600), install.sh читает его и подставляет в шаблон. Гоча идемпотентности: «ставить только отсутствующее» = БИТЫЙ существующий файл никогда не починится установкой — чинить `rm` + повторный install; после любого install верифицировать фактическое содержимое (grep переменных/значений), не вывод скрипта.
- Профилактика диска/памяти теперь активная: Kuma push-мониторы (диск ≥85% → down, RAM ≥90% → down, плюс «Config drift») кормятся cron-ом каждые 5 мин (токены мониторов — /etc/kuma-tokens.env на сервере, порт host:3001) — аларм ловит заполнение ДО смерти PostgreSQL. Плюс cron docker prune (воскресенье 04:45) и swap 2G.
- Пересборка раздутой PG-таблицы (swap-метод) при малом месте: копируй окно с запасом ≥2× на WAL-удвоение (окно «3 дня» падало дважды на 13 ГБ данных при 11–16 ГБ свободных — INSERT упирался в диск и откатывался; выжило окно «1 день»). Порядок swap: сним default → drop старой → rename → НОВЫЙ sequence с setval → default → GRANT-ы приложению (пересозданная от postgres таблица молча теряет права воркеров — INSERT падает, а «воркеры молчат» выглядит как простой конвейера).

## Сайдбар / UX
- Таблицы (решения юзера): числовые колонки — вправо (НЕ центр: разряды встают столбиком, сравнение величин по вертикали), класс `text-right` в паре с уже включённым `tabular-nums`; заголовок повторяет выравнивание своей колонки (числа справа, имена/даты слева). Массовую замену классов по списку имён заголовоков закрывать сверкой ФАКТИЧЕСКИХ текстов `thead th` со списком: заголовок, названный иначе, чем строка в списке замен, молча остаётся со старым выравниванием (колонка съезжает, а тесты зелёные). Порядок блоков сводной страницы — от общего к частному, связанные блоки вместе: KPI → график динамики → таблица по срезу → воронка → топ объектов.
- Форматы в UI (решения юзера, единая точка `src/lib/format.ts`): даты «17.10» (графики) / «17.10.2026» (таблицы) — НИКОГДА ISO-обрезка `slice(5)`; валюта — ТОЛЬКО ₽ (аукцион в RUB; скопированный `$`-форматтер — живой баг). При смене формата отображения грепать тестовое дерево по старому шаблону (asserts матчат старую строку). Никаких локальных fmtMoney-дублей по страницам — только общий модуль. ## Миграции, env, серверные правки
- OpenRTB-контракт (спека 2.5, контрактные тесты, VAST-валидация XSD, wrapper-воронка, диагностика каскада по 204) — references/pacer-umg-integration.md, раздел «OpenRTB-контракт».
- CH-миграции НЕ автоприменяются к живым БД (init-скрипты выполняются только на пустом volume). Теперь идемпотентные ALTER прогоняются деплой-скриптом `deploy/ch-migrate.sh` (ADD COLUMN IF NOT EXISTS) — вызывать его из CD до compose up и вручную на любом стенде перед первым трафиком с новой колонкой; проверка факта: `DESCRIBE ssp.events` на ТОМ стенде, где гоняется consumer, а не «на проде когда-то делал». Dev-стенд отстаёт от прода молча — это и есть механизм дрейфа.
- PG-миграции — та же ловушка, с более жёстким отказом: CD выкатывает код раньше, чем миграция применена → gateway crash-loop `relation "partners" does not exist` (запрос к новой таблице на старте). Диагноз: `docker logs ssp-gateway-1` на «relation ... does not exist»; лечение: применить миграцию (docker exec в ssp-postgres-1 или compose-мигрейшн-сервис), затем `up -d` заново. Правило: **каждая новая миграция = шаг в CD-цепочке до compose up**; после CD сверять версию схемы на проде, а не надеяться, что «применял вручную на dev».
- Удаление поля из записи в CH: clickhouse-go требует scan-destination на КАЖДУЮ колонку таблицы — `MODIFY COLUMN <col> DEFAULT ''` НЕ спасает (проверено на проде), колонку нужно ДРОПАТЬ целиком (`ALTER TABLE ... DROP COLUMN`, в CH это metadata-only). Порядок: дропнуть колонку в CH ДО деплоя кода, убравшего поле из структур, иначе батч-INSERT на живой таблице падает сразу после деплоя; поле у producer и consumer убирать ОДНИМ коммитом — decode строгий (`DisallowUnknownFields`), односторонняя правка режет конвейер. После дропа перезапускать consumer начисто: INSERT, висящий с до-ALTER времён, держит соединение и блокирует цикл вставки даже после успешного ALTER. «Acquire conn timeout» при ЗДОРОВОМ CH (CPU/parts/ошибки в норме — проверять CH первым, не винить его) = утёкшие соединения consumer'а, рестарт коннектора, не тюнинг CH; простой consumer'а данные не теряет — Kafka отбуферизует (полчаса простоя дочитались без потерь после рестарта). Поля-«кэшбастеры» в URL пикселей не путать с колонками CH: они для плеера, их не трогать.
- Гоча compose env: `.env` на сервере НЕ действует, если vps-override жёстко прописывает литералы (`UMG_ENABLED: 0` перебивает). В override — только интерполяция `${VAR:-default}` (для UMG это уже в репо — CD-перезапись compose снесёт серверный хак). После `up -d --force-recreate` проверять ФАКТИЧЕСКОЕ окружение контейнера `docker inspect <c> --format '{{range .Config.Env}}{{println .}}{{end}}' | grep VAR` — `docker compose config` может молчать, а контейнер стартовать со старыми значениями.
- Правка файлов на сервере по ssh: python-heredoc через вложенные кавычки молча не применяется (экранирование) — юзать `sed -i` с якорными паттернами (`^      VAR: literal$`) и сразу `grep`-верификацию результата. Программную замену в ЛЮБОМ файле (python str.replace, sed) верифицировать счётчиком вхождений до/после (`assert old not in text` после замены): несовпавший паттерн даёт молчаливый no-op, и коммит уносит иллюзию правки — баг всплывает на сервере в чужой сессии.

## Observability и денежные инварианты (фиксы аудита)
- Новый денежный путь = новые валидации, которых не было у старого: у external-бидов каскада сравнение с `imp.bidfloor` и отсечение price<=0 НЕ наследуются от direct-пути — проверять ЭТИ два места в каждом новом demand-адаптере (пропущенный floor уходит байеру ниже его минимальной цены, нулевая цена выигрывает аукцион).
- Публичные эндпоинты держать консистентными: добавляешь CORS/HEAD на один (для браузерных инспекторов) — сразу на все sibling'и (/vast, /pvast, /vast-tag), иначе следующий инспектор «не работает».
- Метрики: gateway отдаёт `/metrics` на своём :8080 (route до SPA), consumer — ОТДЕЛЬНЫЙ порт (`METRICS_ADDR`, :9090). Сверять target в `deploy/prometheus/prometheus.yml` с фактическим портом — «скрейпит в пустоту» не падает и незаметен без проверки `curl /metrics | grep ssp_`.
- Видимость no_bid: минутный `ssp.bid_funnel` в CH (req/bid/win/no_bid, SummingMergeTree, TTL 30д) — 204-ответы больше не невидимы для аналитики; воронку в ЛК оценивать на окне от часа после рестарта gateway (in-memory-счётчики метрик при рестарте обнуляются — свежая выборка всегда искажена к no_bid).
- Под нагрузочным тестом сначала КЛАССИФИЦИРОВАТЬ ошибки (по кодам/логам), потом тюнить: хвост 4xx может быть нашими же защитными лимитами (rate-limit байера, QPS-гейт партнёра), а не узким местом — замер чистого пути делать мимо задействованных лимитов и мерить CPU, прежде чем выводить «не вывозим».
- Трекинг-пиксели дублируются ЛЕГИТИМНО (плееры и браузерные инспекторы ретраят трекинг-URL — это норма поведения, не баг клиентов): дедуп обязателен на сервере — consumer режет события по (тип, bid_id) в скользящем окне, quartile/complete-показы считать по уникальным bid_id, а не строкам. Без окна complete задваивается (несколько строк на один bid) и воронка врёт вверх.
- Деньги в CH: агрегаты статистики считать из raw events с дедупом по event_id (argMax) — count() поверх SummingMergeTree-MV задваивает spend при redelivery Kafka (commit-fail после инсерта). Тест: двойная вставка event_id → ровно 1 imp. Rollup (`stats_daily`) обязан воспроизводить ТОТ ЖЕ дедуп-паттерн — числа rollup и raw-пути должны совпадать; интеграционные тесты срезов гонять именно через rollup-путь (фиксированные даты сидов в прошлом автоматически это делают).
- Бюджеты Redis: reserve = один EVAL-скрипт с meta-CAS (смена дневного лимита действует в тот же день, рестарт Redis не сбрасывает потраченное). НЕ lazy-init SetNX полного лимита — это оверспенд.
- Auth: rate-limit логина fail-closed (ошибка Redis → 503); not-found логин сжигает bcrypt на dummy-хэше (анти-тайминг).
- После subagent-раунда с усечённым отчётом (max_iterations) проверять `git status` — хвостовые lint-фиксы остаются некоммиченными; докоммитить и прогнать build/vet/lint самому перед push.

## Контрактная целостность (schema-drift)
- Consumer round-trip ловит баги в ОБЕ стороны: прогон нашего артефакта через НАСТОЯЩИЙ парсер потребителя (не копию!) с инвариантами на распарсенные поля нашёл баг уже в самом парсере pacer: `if not child` на `ET.Element` — falsy для элементов без детей (deprecated `bool(Element)`), текстовые опциональные дети (`<AdSystem>ssp</AdSystem>`, AdTitle, Description) молча терялись при зелёных тестах. Правило Python: на `ET.Element` проверять `is None`, не truthiness. Раннер — `scripts/pacer_parse/parse.py` (импортирует настоящий парсер, отражает распарсенные поля в JSON). Свой зеленый тест на свой артефакт потребителя не проверяет — валидировать и XSD-эталоном, и round-trip'ом.
- Kafka-событие живёт в 4 местах: `tracking/event.go` (producer) ↔ `consumer/event.go` ↔ CH-inserter ↔ `clickhouse/init/*.sql` — новое поле = правка ВСЕХ четырёх, дрейф молчалив. Consumer decode строгий: `DisallowUnknownFields`, отсутствие `ts` — ошибка строки (не `time.Now()`); не-UUID `event_id` отбрасывать ПОСТРОЧНО с метрикой `ssp_consumer_events_dropped_total` — вечный retry всего батча на CH-ошибке вставки = poison pill: один битый event стоит весь конвейер.
- MSW-моки фронтенда расходятся с реальным JSON бэка молча — «мок валидирует мок». Типы `api.ts` сверять с фактическим marshaling'ом admin-хендлеров; для форм — golden-JSON реального ответа как shared fixture.
- Частичный PATCH: бэк мержит пустые поля креатива с текущими (пусто = «не менять»); фронт шлёт фактические значения, не хардкод-дефолты (640×480 в теле PATCH молча затирал click_url/title/размеры кампаний, созданных вне UI).
- Партнёрский nurl дёргать после резолва OpenRTB-макросов (`${AUCTION_PRICE}` и пр., эталон — pacer `nurl_macros.py`) — литеральный GET не атрибутирует их win; `bid.cur` ≠ RUB → no-bid, не писать чужую валюту как RUB (инфляция spend в разы).
- Пиксельные роуты — method-check GET/HEAD: OPTIONS/POST с query публиковали события (preflight браузерного инспектора = дубль quartile). Фикс-валидация: 405 и ноль событий в тесте.
- Вводя инвариант на уровне конвейера (дедуп по ключу, уникальность event_id), грепать СИДЫ тестов по лениво переиспользуемым ключам: фикстуры, шлющие N событий под одним bid_id/event_id, теперь падают ЛЕГИТИМНО (инвариант режет их до 1) — чинить сиды (уникальный ключ на логическую сущность), а не ослаблять инвариант.
- Доменное поле без генерации = мёртвый контур: click_url в БД и /clk-роут ничего не делают, пока VAST-генератор не эмитит <VideoClicks> (ClickThrough из click_url + ClickTracking на /clk), а потребитель не парсит блок. Аудит класса «существует, но мертво»: сверять 4 поверхности — спека VAST ↔ что генерим ↔ что парсит pacer ↔ какие пиксели реально в роутах; каждая, на которую никто не ссылается, — кандидат. Триаж хвостов аудита — три корзины: (1) мёртвую ЗАПИСЬ удалять (поле без читателя = долг), кроме резерва под известную будущую фичу — тогда комментарий в DDL; (2) дешёвую симметрию чинить (парсится, но не используется потребителем — дотащить до конца); (3) осознанное «не строим до потребителя» ПИНИТЬ: YAGNI-комментарий на месте эмитта (список сознательно неэмитимых опционалов и почему) + НЕГАТИВНЫЕ ассерты в контракт-тесте (сгенерённый VAST не содержит запрещённых полей; RED-доказательство — инжект атрибута в генератор падает тестом). Без пиннинга мёртвые поля тихо возвращаются при следующей фиче. Wrapper'у ставить allowMultipleAds=false — partner-VAST с 2+ Ad иначе валит показ.
- «В VAST нет кликов» — сначала проверить click_url креатива: генератор корректно опускает <VideoClicks> при пустом click_url, и тестовый тег молча уходит без кликов.
- Симуляционные события генератора трафика (вероятностные фейковые клики и т.п. — механизмы для проверки трекинга) НЕ живут в проде: playback-воркер эмитит их как подлинные, они доезжают до реальной статистики SSP, и «откуда клики» — вопрос клиента, а не теста. Найденный в проде симулятор вырезать ВСЮ поверхность одним коммитом — константа, точка вызова в flow, парсинг блока, поля сущностей, тесты — а не занулять вероятность дефолтом (занулённый дефолт возвращается следующей правкой дефолтов). Верификация вырезания — фактом данных: рестарт воркеров генератора (CD их не трогает), затем ноль событий этого типа в CH при продолжающихся показах; «0 imps в 2-минутном окне» НЕ означает смерть конвейера — трафик порывистый и зависит от часа, окно расширять до 10 мин, прежде чем искать поломку.
- ip/ua пикселей зашивать в query при ГЕНЕРАЦИИ VAST (из device бида), фолбэк на ClientIP/UA запроса: ClientIP приходит С портом (ip:port), гео-lookup по такой строке падает в датацентр, а ip прокси плеера как «страна» искажает срез.
- Контракт кликов — round-trip: наш VAST через НАСТОЯЩИЙ парсер pacer с инвариантами на VideoClicks/InLine-ошибки/число Ad; тест писать RED до фикса парсера (до фикса assertion на video_clicks падает — это и есть ловля бага).

## Фронт-тесты: гоча
- Статус прогона vitest читать по СТРОКЕ `Test Files`, не только по `Tests`: при ошибке трансформации/краше уровня файла пишется «2 failed | 15 passed (17)» при «Tests 101 passed (101)» — grep только по `Tests ` показывает зелёный на красном наборе.
- Программную перестановку JSX-блоков (python/regex по pages/*.tsx) после себя ВСЕГДА закрывать `tsc --noEmit` + прогоном компонентных тестов: правило блоков незаметно задваивается, а хвостовые `</div>`/`)` теряются (страница перестаёт компилироваться целиком — тесты сресят это как file-level failure, см. пункт выше). Один tsc-прогон дешевле дебага красного CD.
- Файл с JSX в тесте называть `.test.tsx`, не `.test.ts` — иначе «Unterminated regular expression literal» (tsx в .ts не парсится).
- Зелёный vitest ≠ зелёный CD: docker-build гоняет `npm run build` (tsc со strict-флагами tsconfig.app.json — noUnusedLocals/noUnusedParameters), неиспользуемый параметр в тестовом колбэке или лишний импорт валит сборку прод-образа. Перед пушем фронта прогонять `npm run build`, а не только тесты.
- MSW-хелпер `json(data, status = 200)` принимает статус ПОЗИЦИОННЫМ числом — axios-стиль `json(body, { status: 201 })` не компилируется (тип хелпера — number, не RequestInit).
- В vitest-тестах читать файлы через `process.cwd() + '/src/...'`, не `new URL(..., import.meta.url)` — в jsdom-среде import.meta.url имеет http-схему и readFileSync падает «The URL must be of scheme file».

## Интеграционные тесты: гоча
- Тестируя конкретный SQL-констрейнт (UNIQUE, FK), заполняй ВСЕ поля валидными значениями: zero-value struct (TimeoutMs: 0) упадёт по раннему CHECK-констрейнту вместо целевого UNIQUE — тест проверяет не то, что задуман, и ломается при любом изменении схемы.
- Тестовый контейнер обязан применять ВСЕ init-файлы прод-схемы (ddlFiles-список = полный `clickhouse/init`): пропущенный дроп-миграционный файл дал «missing destination name cb» — расхождение тест-схемы с прод-схемой бьёт AppendStruct, а не тест. Тестовый DDL-сплиттер режет файл по «;» — сначала вырезать `--` комментарии: комментарий с точкой с запятой разваливает statement молча.
- Прогон integration на Mac флейкает через testcontainers/ryuk: перед прогоном чистить мёртвые контейнеры `docker rm -f $(docker ps -aq --filter status=created)`; медленный первый прогон после падения Docker (до ~15 мин).
- Race в тестах таймаутов (tmax запроса == таймауту партнёра): дочерний ctx не должен наследовать родительский дедлайн 1-в-1 — иначе взаимная гонка «кто первый отменит» даёт флейк; тестируй поведение, а не точные тайминги.
- Перед пушем после subagent-раунда: `go test -race ./...` + `go test -tags integration -count=1 ./...` прогонять самому — отчёт агента может быть усечён, а зелёный vitest не покрывает Go-тесты.
